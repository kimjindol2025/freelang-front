# FreeLang Front Roadmap

> 목적: FreeLang Front를 “페이지 렌더러”가 아니라, 실사용 프론트엔드 언어로 완성한다.
> 기준: 기능 추가 수보다 언어 완성도, 반복 가능성, 디버깅 가능성, 운영 안정성을 우선한다.

## 1. 목표

FreeLang Front의 목표는 다음 여섯 가지를 동시에 만족하는 것이다.

- 문법과 의미론이 흔들리지 않을 것
- 컴포넌트/Island 모델이 일관될 것
- 상태/라우팅/폼/이벤트가 표준 패턴으로 정리될 것
- 빌드/HMR/디버깅 체계가 안정적일 것
- 예제/가이드/템플릿이 신규 진입을 돕는 수준일 것
- 중간 규모 앱을 FL만으로 유지할 수 있을 것

## 2. 추진 원칙

- 기존 FL 코어와 현재 운영 경로는 유지한다.
- 새 기능보다 표준화와 안정화를 먼저 한다.
- 서버와 브라우저에서 같은 개념이 읽히도록 맞춘다.
- 가능한 기능보다 반복 가능한 패턴을 먼저 고정한다.
- 구현은 작게, 계약은 명확하게, 검증은 자동화한다.

## 3. 단계별 로드맵

### 1단계 — 언어 코어 고정

목적: 문법과 의미론을 흔들림 없는 상태로 만든다.

핵심 작업:

- 문법/의미론 기준 정리
- 에러 메시지 안정화
- 표준 라이브러리 경계 정리
- 서버/브라우저 공용 규약 확정
- 빌드 실패와 런타임 실패의 책임 경계 분리

완료 기준:

- 같은 입력은 항상 같은 빌드 결과를 낸다.
- 대표 문법 오류가 일관된 메시지로 나온다.
- 코어 변경 없이도 문서만으로 사용 가능하다.

### 2단계 — 컴포넌트 / Island 모델 정착

목적: UI를 조립하는 방식을 표준화한다.

핵심 작업:

- 상태 훅 / atom / store 모델 정리
- props / state / event 패턴 고정
- 재렌더 규칙 명확화
- 직접 DOM 조작을 최소화하는 가이드 정리
- Island 내부와 외부의 책임 분리

완료 기준:

- 같은 UI 작업이 여러 방식으로 쓰이지 않는다.
- 상태를 두는 방식이 예측 가능하다.
- 클릭/입력/리렌더 패턴이 앱 전반에서 일관된다.

### 3단계 — 프론트 실사용 패턴 확보

목적: 실제 제품 앱에서 자주 나오는 화면을 언어 차원에서 안정적으로 다룬다.

핵심 작업:

- 라우팅 표준화
- 폼 처리 표준화
- 데이터 fetch 패턴 고정
- 리스트 / 테이블 / 모달 / 탭 / 검증 패턴 정리
- 에러 경계와 로딩 경계 공통화

완료 기준:

- CRUD 중심 화면을 반복 구현할 수 있다.
- 페이지마다 임시 코드가 아니라 같은 패턴으로 작성된다.
- 에러, 로딩, 비어 있음 상태가 일관되게 처리된다.

### 4단계 — 개발자 경험 정리

목적: 만들 수 있을 뿐 아니라 계속 고치고 추적할 수 있게 한다.

핵심 작업:

- HMR 정리
- source map / line mapping 정리
- 브라우저 콘솔 대응 체계 정리
- build / watch / serve 명령 표준화
- 테스트 헬퍼 정리

완료 기준:

- 수정 후 재확인이 빠르다.
- 에러 위치 추적이 가능하다.
- 개발 서버와 운영 서버의 차이가 문서화된다.

### 5단계 — 생태계와 문서

목적: 신규 개발자가 빠르게 들어올 수 있게 만든다.

핵심 작업:

- 예제 앱 묶음 구성
- 공식 스타일 가이드 작성
- 템플릿 제공
- CLI / 스캐폴딩 정리
- migration guide 작성

완료 기준:

- 첫 화면 수정 경로가 문서와 일치한다.
- 예제만 따라도 기본 앱을 만들 수 있다.
- 기존 코드와 새 코드가 같은 규칙을 쓴다.

### 6단계 — React / Vue급 판단 기준 충족

목적: “기능이 있다”가 아니라 “독립 사용 가능하다”를 판정한다.

판단 기준:

- 중간 규모 앱 1~2개를 FL만으로 유지 가능
- 신규 개발자가 1일 안에 첫 화면 수정 가능
- 에러 원인 추적이 가능
- 배포와 롤백이 안정적
- 언어를 쓰는 이유가 문서상 설득 가능한 수준

이 단계는 기능 추가가 아니라 운영 결과로 판정한다.

## 4. 성공 지표

정성 지표:

- 문법 설명이 짧아진다
- 예제 앱마다 작성법이 달라지지 않는다
- 에러가 나도 원인 파악이 가능하다
- 문서를 보고 바로 첫 구현이 가능하다

정량 지표:

- 빌드 통과율
- 브라우저 smoke 성공률
- HMR 복구 성공률
- 주요 화면군 재사용률
- 신규 작성 코드에서 표준 패턴 준수율

## 5. 범위 가정

- 현재의 `SSR + Island` 구조는 유지한다.
- 기존 FL evaluator와 현재 운영 경로는 유지한다.
- 방향은 React/Vue의 복제가 아니라 FL 자체의 완결성 강화다.
- 대규모 생태계 모사는 하지 않고, 실사용에 필요한 최소 완결성을 먼저 달성한다.
- 운영 자동화와 문서화는 부가물이 아니라 완료 조건의 일부다.

## 6. 범위 밖

이 로드맵은 다음을 목표로 하지 않는다.

- React/Vue API의 직접 복제
- 기능 수를 빠르게 늘리는 방식
- 코어 언어를 무리하게 재설계하는 방식
- 현재 동작 중인 FL 프론트 경로를 깨는 변경
- 즉흥적인 하드코딩 데모
